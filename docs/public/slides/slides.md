## GitHub Pages に全部載せる

| パス | 中身 |
|---|---|
| `/` | ダッシュボード（ゴール・進み具合・判断待ち） |
| `/spec/` `/open-questions` | 仕様と未解決論点 |
| `/app/` | MSW 入りのアプリ（触れる仕様書） |
| `/api-docs/` | API ドキュメント（zod → OpenAPI → Redoc） |
| `/e2e-report/` `/vitest-report/` | テストレポート（E2E はスクショ付き） |
| `/process/timeline` | 体制の進化のタイムライン |
| `/slides/` | このスライド（reveal.js） |

<small>main に push するたび、GitHub Actions が全部ビルドし直す</small>

## 方針：状況を手で書かない

```text
docs/backlog/*.md   1要望1ファイル。frontmatter に状態・判断待ち
docs/roadmap.md     ゴールとマイルストーンの定義
docs/open-questions.md / known-issues.md / evolution.md
        │
        │  ビルド時に docs/.vitepress/*.data.ts が集める
        ▼
   トップページのダッシュボード
```

- 進み具合を書き写さない。ファイルを1つ直せば、ダッシュボードも直る
- ロードマップに無いマイルストーンを書くと、**ビルドが止まる**

---

## ダッシュボードは読み手ごとに

- **全体** … ゴールとマイルストーン、いま取り組んでいる所の残り
- **PO 向け** … 決めないといけないこと（要望の判断待ち・未解決論点）
- **開発者向け** … 要望ごとのサイクルと PR、既知の問題、進化ログの未評価の候補

人間は「判断待ち」を見て決めるだけ

Note:
AI は判断が要ると、要望ファイルの status を「判断待ち」にして decisions に書く。それがそのまま出る。

---

## API ドキュメントも書き写さない

```text
packages/schemas の API の一覧（zod）
   ├─▶ OpenAPI 3.1 の文書 ─▶ redocly lint ─▶ Redoc の HTML
   └─▶ テスト：MSW のハンドラと一覧が1対1か
              返した応答がすべて一覧の形どおりか
```

- ハンドラを足して一覧に書き漏らすと、テストが落ちる
- バックエンドができたら、同じ一覧を契約テストに使う

## 開発サイクル（1機能 = 1サイクル）

```text
1. プラン作成（AI がインタビュー、人間が答える）
2. プランの AI レビュー
3. テスト網羅レビュー
4. 実装
5. テスト全通過（TDD：先に Red を確かめる）
6. 実装の AI レビュー（3体並列：設計／異常系／仕様）
7. 人間レビュー（AI が画面を操作して説明、人間が判定）
8. push・振り返り
```

- 正は `docs/process/`、入口はツール非依存の `AGENTS.md`
- Claude Code の skills・サブエージェントは **呼び出し口だけ**

---

## 人間がやるのは3つだけ

1. プランのインタビューに **答える**
2. 人間レビューで **判定する**（AI に判定させない唯一の型）
3. 振り返りで改善案を **採用／却下する**

lint・型検査・テスト・docs ビルドは git フックと CI が止める<br>→ AI にも人にも「確認して」と頼まない

---

## サイクルを軽く回す工夫

- **セッションを分ける** … プラン／実装〜人間レビュー／振り返り
  - <small>本家の集計：1サイクルを1セッションで通すと、1ターンで平均30万〜50万トークンを読み直していた</small>
- **モデルを段で割り当てる** … 強い（設計）／標準（実装・照合）／軽い（調査）
- **pre-push は成功したら1行** … AI が push すると出力が全部会話に入るため

---

## もう1つのループ：体制の進化

```text
開発サイクル ──振り返り──▶ 候補
                             │
                      人間が採用／却下
                             │
         ルール・スキル・フック・CI を更新
                             │
                  次のサイクルへ ◀┘
```

ゲーム本体の「進化候補の評価」と **同じ型** で、<br>開発プロセス自体を進化させる。**却下も理由つきで残す**

---

## 記録の型 → タイムライン

```text
### 2026-10-15 API ドキュメントと E2E も基盤に入れた
- … 反映先：packages/schemas/・scripts/build-api-docs.ts …
  - きっかけ：人間の要望 ／ 止め方：機械（ビルド時の自動生成）
```

- **きっかけ** … 人間レビュー／AI レビュー／作業中の失敗／人間の要望／計画
- **止め方** … 機械／レビュー観点／手順・ルール／置き場所
- 読めない書式は **ビルドが止める**。進め方を変えて記録しないコミットは **commit-msg フックが止める**

---

## 改善は「注意」ではなく「仕組み」で

| 本家で起きたこと | 止め方 |
|---|---|
| AI が heredoc でスクリプトを書き、バックスラッシュが崩れる（2回） | Claude Code のフックで止める |
| AI が勝手に `--no-verify` | フックで止める |
| 用語の揺れ（制作者／作者…） | ビルドで旧称を検出 |
| 進化ログの書き忘れ | commit-msg フック |
| 依存の向きを自前テストで検査 | Biome のルールに置き換え |

ルールを読ませるだけでは、**モデルや担当が変わると崩れる**

## …やりすぎた

本家の 2026年10月前半

- 進め方を変えたコミット **76** ／ コードを変えたコミット **78**
- 振り返りの改善候補が **ほぼ全件採用**

→ 改善のための改善で、機能が進まない

## 楽観ロックでリスクをとる

> 100% を求めない。失敗したら対応できるようにしておけばよい

- 楽観ロック：先にロックせず進め、ぶつかったときだけ直す
- 開発体制に当てはめると…
  - 前もって全部を防ごうとしない
  - **失敗に気づいて戻せる仕組み** があれば、前段の関門は緩めてよい

---

## 戻せる仕組みは、もうある

- pre-commit … lint（安全な修正は自動で当てる）
- pre-push … 型検査・テスト・docs ビルド・API ドキュメント
- CI … 同じチェック＋E2E
- Pages … テストが落ちても、落ちたままのレポートを載せる

→ だから **前段を軽くできる**

---

## 完璧主義で進めないための決まり

- **仕組みにするのは2回目から**
  - 1回目の失敗は候補に記録するだけ
  - 例外：戻せない失敗（データや未コミットの変更が消える、気づかず main に入る）は1回目から止める
- **P2 の指摘は直さず、1行記録して終わる**
- **プランのレビュー観点は、プランの中身で絞る**
- **今の開発フェーズに見合う設計** … 使う場所の無い拡張点・旧データの互換は作らない

<small>本家で人間が却下した4件の理由は、どれも「1回で、気づいて直せた」だった</small>

## このサンプルでの実例

進化ログの候補（未評価）より

- 画面が API の一覧を import するのを **lint で止めない**
  - いまはルールの文書だけ。違反が1回起きたら入れる
- リクエストの本文の検査は **まだ入れない**
  - 本文を受け取る API が無い。最初に要るサイクルで入れる
- 依存の向きの lint・左メニューの検査も **候補止まり**

<small>入れなかったことも、理由つきで残す</small>

## まとめ

- **状況は書き写さず、ビルドで組み立てる**<br>ダッシュボード・タイムライン・API ドキュメント
- **人間は判断だけ**、確認は機械に寄せる
- 開発プロセスも **候補 → 評価 → 採用／却下** で進化させる
- ただし仕組みも重さになる。**楽観ロックで、2回目から**
